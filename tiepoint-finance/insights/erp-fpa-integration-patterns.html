ERP-to-FP&A Integration Patterns

Native connectors, iPaaS, APIs, saved searches, ODBC and SFTP: how each pattern works, what it costs you in reliability and control, and the specifics for NetSuite, Business Central, SAP, Sage Intacct, QuickBooks Online and Xero.

Key takeaways

  • Choose the integration pattern per source, by reliability and ownership, not by novelty. A well-run scheduled file can be more dependable than a fragile API script.
  • Extract trial-balance-grade data: balances or GL detail that can be tied to the ledger by entity, period and account. Pre-aggregated report exports are hard to reconcile.
  • Incremental loads need a safety net. Late journals and back-dated postings are routine, so re-pull a rolling window of recent periods on every run.
  • Put data quality gates between extraction and publication: row counts, debit-credit balance, unmapped accounts, period coverage, and a trial balance tie.
  • Integration identities must be least-privilege, read-only where possible, and owned by you. Several ERPs now favor certificate-based or client-credential authentication for unattended integrations.

Who this is for: finance systems managers, controllers and FP&A leaders deciding how actuals should flow from one or more ERPs into a planning or reporting platform, and IT or data teams asked to support that flow.

The integration patterns

Pattern How it works Strengths Watch-outs
Native connector (built by the FP&A vendor) The platform connects to the ERP's API with its own connector and mapping layer Fastest to stand up; vendor maintains it You inherit the vendor's extraction logic. Confirm exactly which fields, books and periods it pulls
iPaaS (for example Workato) An integration platform runs "recipes" that read from the ERP and write to the target Reusable, monitored, handles many systems Another subscription and another skill set; per-record limits on some actions
Direct API Custom code calls the ERP's REST or SOAP API Full control You own maintenance, rate limits, paging, retries and authentication renewals
Query / saved search A saved query or report in the ERP is exported on a schedule or read by API Finance can see and adjust the logic Logic drifts if someone edits the saved search; needs change control
ODBC / JDBC Read-only SQL access to an analytics data source Efficient for large volumes Driver installation, network access, schema knowledge
File / SFTP ERP produces a file; the platform picks it up Works with any system, including on-premises Scheduling, file naming, partial files, and who notices when it does not arrive
Data warehouse ERP data lands in a warehouse; the FP&A platform reads from it One governed copy for BI and FP&A Warehouse logic becomes part of the reconciliation chain

How we choose. For each source, we ask four questions in Discover: Does a maintained native connector exist and does it pull what we need at the grain we need? Who will own the integration after handover? What volumes and refresh frequency are needed? And can we tie its output to the trial balance? The answer is often a mix: a native connector for the main ERP, a file feed for a legacy ledger, and a warehouse connection for operational data.

What to extract

Balances versus detail

  • Trial balance by entity, period and account (plus dimensions). The minimum for management reporting and the easiest to tie out.
  • GL detail (journal lines). Needed for drill-down, transaction-level analysis and allocations. Larger volumes, and must sum exactly to the balances.
  • Master data. Accounts, entities, departments and other dimensions, currencies, exchange rates, fiscal periods. These change, and a load without current master data produces unmapped lines.

Fields that must come with every line

Entity (subsidiary or company), accounting book or ledger, fiscal period, posting date, account, all reporting dimensions, intercompany partner where relevant, amount in transaction currency, amount in functional currency, currency codes, document reference, and a last-modified timestamp for incremental loads.

Refresh cadence, and incremental versus full loads

Cadence. Match the cadence to the decisions the data supports. Daily refresh is common during close and for cash; monthly is enough for many planning cycles once periods are locked. More frequent is not automatically better: each refresh is a chance for a partially posted state to appear in a report.

Full load. Re-extract everything in scope each time. Simple and self-correcting, but slow at volume and heavier on API limits.

Incremental load. Extract only records changed since the last successful run, using a last-modified timestamp. Efficient, but fragile in specific ways:

  • deleted or voided transactions may not appear as "changed",
  • journals posted into a prior period carry a recent modification time but an old period,
  • clock and time-zone differences between systems can skip records at the boundary.

Our default design: incremental for the open period, plus a rolling re-pull of the last few closed periods on every run, plus a full reload of the current fiscal year on a schedule (for example weekly during close season). Combined with the "Late Journal" test in our tie-out playbook (re-extract prior periods and compare to the stored snapshot), this catches the changes incremental logic misses.

Data quality gates

Data should not be published to users until it passes automated gates. A practical set:

Gate Test Action on failure
Completeness Row counts and period coverage versus the previous run and versus the source Block publication; alert owner
Balance Debits equal credits per entity and period Block
Mapping Unmapped accounts and dimension values = 0 Hold in suspense line; block release
Tie-out Loaded totals equal the trial balance per entity, per month Block release of affected reports
Freshness Load timestamp within the expected window Banner on reports; alert
Rates Rate table present for every currency and period in scope Block translation

These gates map directly onto the Five Tie-out Checks we use as the release gate in the TiePoint Method.

Audit trail

For every load, keep: the run identifier and timestamp; the source query or connector version; parameters (entities, periods, books); row counts and control totals; the gate results; and who approved publication if approval is manual. Several FP&A vendors describe sync logging in their own platforms (Cube, for example, states that every sync is logged), but keep your own control totals as well, so that the evidence does not depend on one tool.

Security

  • Dedicated integration identity. Never an individual's login. The account belongs to the company and is documented in the runbook.
  • Least privilege. Read-only access to the records the integration needs, nothing more.
  • Strong, non-interactive authentication. Certificate-based or client-credential flows rather than shared passwords. Delegated sign-in flows can require multi-factor authentication, which is right for people and wrong for unattended jobs; use the ERP's supported service-to-service method instead.
  • MFA for every human who administers the integration, the FP&A platform or the ERP role.
  • Credential ownership. Secrets and certificates are created and stored by the client, with expiry dates in a calendar. Expired certificates are a common cause of a "Stale Snapshot" failure.
  • Environment separation. Sandbox and production use separate credentials. Check whether a sandbox refresh wipes integration setup.

ERP specifics

Oracle NetSuite

  • SuiteAnalytics Connect provides ODBC, JDBC and ADO.NET drivers and, in Oracle's words, "a read-only method for obtaining NetSuite data." It accesses data through the NetSuite2.com data source, which applies role-based access control. Oracle states that the older NetSuite.com data source is no longer available as of NetSuite 2026.1, and that connections must use certificate-based server authentication and provide the Account ID and Role ID. Oracle also advises that the Connect Service should be used with static data or data that doesn't change often, rather than real-time access.
  • SuiteQL over REST. Queries are sent by POST to the /services/rest/query/v1/suiteql endpoint with a required Prefer: transient header. Oracle documents a maximum of 100,000 results per SuiteQL query and recommends SuiteAnalytics Connect for larger result sets.
  • Authentication. NetSuite supports OAuth 2.0 client credentials (machine-to-machine): an integration record with the client credentials grant enabled, a certificate, and a mapping to an entity and role. Two operational details matter: a maximum of five active certificates per integration, entity and role combination; and the setup is not copied between accounts, and is cleared each time a sandbox is refreshed. Token-based authentication remains in use by many connectors; Workato's NetSuite connector, for example, documents token-based authentication.
  • Saved searches. Many connectors and iPaaS tools can trigger on or read saved search results (Workato lists saved search triggers). If a saved search is part of the integration, lock it down: restrict edit rights, name it clearly, and record its definition in the runbook.
  • Consolidated rates. NetSuite holds Current, Average and Historical consolidated rates per subsidiary and period. Pull them with the data rather than recalculating them.

Microsoft Dynamics 365 Business Central

  • APIs. Business Central online exposes standard APIs (v2.0), enabled by default, including a generalLedgerEntry resource with posting date, account number, debit and credit amounts, dimension set lines and a read-only lastModifiedDateTime that supports incremental extraction. Standard APIs cannot be extended with extra fields; Microsoft advises copying the API code into a custom API if you need more.
  • Service-to-service authentication. Microsoft documents the OAuth 2.0 client credentials flow for unattended integrations: register an app in Microsoft Entra ID, then register it in Business Central's Microsoft Entra applications page and assign permission sets. Microsoft states that applications can't be assigned the SUPER permission set and should follow the least-privilege principle. Microsoft notes delegated flows can require MFA, which prevents unattended integrations.
  • Limits. Microsoft's operational limits for OData requests include a per-user rate of 6,000 requests in a 5-minute sliding window, 5 concurrent requests (extra requests queue), a maximum page size of 20,000 entities and an 8-minute operation timeout. Design paging and retries around these.
  • Consolidation. Business units can share data with the consolidated company by database, API or file, and accounts carry a consolidation translation method. If the FP&A platform does the consolidation instead, decide which system is authoritative.

SAP S/4HANA

SAP provides standard OData APIs for balance reporting. An SAP Community article on S/4HANA Cloud balance reporting describes a Read Trial Balance API (based on the Trial Balance app, with aggregation level set through $select, for example by G/L account and profit center) and a Read Journal Entry Items API that returns line items which can be aggregated into balances. In SAP landscapes, confirm early: the ledger and company codes in scope, whether the organization already exposes finance data through a data platform or warehouse, and who in the SAP team owns the service user and its authorizations.

Sage Intacct

Sage Intacct's documented web services use an XML API over HTTP POST. Access requires a Web Services sender ID (authorized for each company) and company credentials. Sage strongly recommends a dedicated Web Services user, which typically has no UI access, and recommends session-based authentication. The documentation notes queries should return fewer than 1,000 records per page. Sage Intacct's dimensions (location, department, class, project and others) map naturally to FP&A dimensions; Cube, for example, describes carrying Sage Intacct dimensions and statistical accounts into reports and plans.

QuickBooks Online

Intuit's developer blog (in a 2016 post; confirm the current figures in Intuit's developer documentation) states that API calls are throttled at 500 requests per minute per realm ID (one QuickBooks company), including batch requests, and that an application cannot make more than 10 concurrent requests to the same realm. Groups often run one QuickBooks company per legal entity, so the integration must handle many realms and consolidate them; Cube, for example, describes consolidating actuals from every QuickBooks file into one view.

Xero

Xero documents per-tenant (per organization) limits of 5 concurrent calls, 60 calls per minute and 5,000 calls per day, plus an app-wide limit of 10,000 calls per minute across all tenants. Exceeding a limit returns HTTP 429 with a Retry-After header. Xero recommends the If-Modified-Since header to retrieve only changed records, and supports paging (100 records per page) on major endpoints. For multi-entity groups on Xero, the daily limit per organization is the constraint to design around when you need full reloads.

Artifact: integration design checklist (per source)

  • Pattern chosen and reason recorded (native, iPaaS, API, query, ODBC, file, warehouse)
  • Data scope: entities, books, periods, accounts, dimensions, currencies
  • Grain: balances, GL detail, or both, and how detail sums to balances
  • Master data included: accounts, dimensions, periods, rates
  • Integration identity created in the client's name, read-only, least privilege
  • Authentication method documented, with secret or certificate expiry dates
  • Rate limits, paging and retry logic designed and tested
  • Incremental logic plus rolling re-pull of recent closed periods
  • Data quality gates defined, with action on failure
  • Failure alerting to a named owner, and a report banner for stale data
  • Audit trail: run ID, parameters, row counts, control totals
  • Sandbox and production separated; effect of sandbox refresh known
  • Runbook entry: how to rerun, how to rotate credentials, who to call
